# Compiler architecture audit validation

Date: 2026-09-10. Scope: the active Haskell compiler and interpreter in `src/Jazz/Compiler`, with callers and tests inspected where they establish a boundary or observable behavior.

This validates the three supplied audits against code. It does not treat agreement between auditors as corroborating implementation evidence. The reviewed checkout is `934802131e74f6833aabebf934cdaa0e179df81c`; compiler, runtime, CLI, hosted sources, and tests are unchanged from `2695289b1e9a7555855eb6b00147a478ae010c6d`, the first audit's source baseline. No compiler behavior was changed during validation.

The implementation proposal is in the [remediation plan](2026-09-10-compiler-architecture-remediation.md). This report records the evidence, qualifications, and rejected recommendations that constrain it.

## Conclusion

The central diagnosis holds: several phases independently recover lexical identity, scope structure, module visibility, declaration meaning, and execution decisions. The largest simplification opportunity is to establish those facts once and make downstream consumers use them.

That does **not** validate every proposed deletion. Jazz already has typed phase boundaries and a shared expression evaluator. Its runtime does not consume the inference state's fact maps directly. A module sequence plus an index is sensible, constructing an `EBlock` wrapper does not copy its statements, and explicit exit, runtime failure, compilation failure, and valueless success must remain distinct. Neither the comparisons nor the audits establish a defensible net line reduction estimate.

The proposed direction is an interpreter with one authoritative analyzed expression form, stable declaration identities, one program construction path, complete semantic module interfaces, and shared lexical execution rules. It retains necessary inference state, diagnostics, lazy cells, runtime representations, and dynamic specialization. It introduces no speculative backend, generic pass framework, cache format, or user-visible language changes.

## Additional claims and corrections

### Metadata that runtime does not read is not automatically dead

The runtime primarily uses execution plans, declaration facts, and specialized runtime representations. Several expression fields have no direct runtime reader. Nevertheless, E17 explicitly checks complete analyzed facts, numeric operand decisions, literal ranges, generalized schemes, and definition-site binder identity. The plan preserves an inspectable semantic analysis product. It may change tests coupled to the old six-map attachment protocol, but must replace their semantic assertions, not erase coverage to make fields removable.

Similarly, constructor/method facts are already normalized in analyzed declarations. A claim that the runtime universally reparses source declarations is false. Remaining normalization should move upstream from attachment and interface rebasing, not duplicate the normalized declaration work that already exists.

### Speculation is not one universal rollback

E04 shows incompatible restoration policies with intentional effects. Preview inference discards semantic state but advances the fresh-variable watermark; skipped pattern inference restores the stable state while preserving emitted errors. A single generic “rollback everything” operation would be wrong. T09 makes these two named operations explicit and leaves necessary type inference intact.

### Stable binding identity does not remove all runtime discovery

Compile-time resolution can publish declaration IDs, lexical groups, and capture candidates. It cannot determine which callable a runtime condition selects. Runtime initialization/selection remains responsible for values, blackholes, laziness, host effects, and branch-dependent callable aliases. “One scope owner” means one lexical interpretation, not one algorithm pretending to do every phase's job.

### Interface completeness needs two boundaries

Module discovery needs exported names before dependency type inference is complete. A cheap declaration/export inventory is therefore justified. Separately, successful analysis should publish an interface sufficient for downstream typechecking without access to the resolved dependency body or separate binder/evidence sidecars. Public visibility must remain separate from the module's private environment: tests explicitly preserve private declaration information while restricting published exports. T08 does not collapse those distinct concepts into one unfiltered record.

### Historical explanations and line savings

For planning constraints only, the current accepted [RFC 0016](../../rfcs/accepted/0016-optional-backend-removal.md) explicitly retains runtime plans while removing the optional backend. The code-based criticism of derived runtime obligations remains valid, but their removal requires a targeted change to that retained architectural decision. T11a records this dependency; the audit does not treat all observed complexity as already authorized for deletion. Retired backend designs are not used as evidence or as a reason to reintroduce an IR.

The proposed sequence “new features accumulated around an unchanged backbone” is a plausible explanation of the code's shape, not a verified development history. No git-history causal analysis was performed, and no conclusion attributes this to a person, agent, or development process.

The B estimate of 3,000–7,000 net removable lines, its 5,000-line center, and C's four component bands are **unsubstantiated**. There is no completed alternative implementation, deletion inventory with replacement costs, or measured sample from which to infer these ranges. Some apparent savings concern justified structures; stable identity and better contracts will also add code. C's comparison cannot validate a savings estimate. The undocumented earlier “-250” estimate has no evidentiary role here.

Success should be measured by eliminated reconstruction paths, narrower dependencies, fewer representations of the same decision, and preserved behavior/performance. Record actual net changes after implementation, without making a size target a correctness constraint.

### Elm

At `1bd5b36915a38335195ca7792fe3995f53d84d5e`, [Compile.hs](https://github.com/elm/compiler/blob/1bd5b36915a38335195ca7792fe3995f53d84d5e/compiler/src/Compile.hs#L35) performs canonicalization, typechecking, pattern checks, and optimization. It returns `Artifacts` containing a canonical module, a map of annotations, and an optimized local graph. It does **not** generate JavaScript in that function. [Canonical syntax](https://github.com/elm/compiler/blob/1bd5b36915a38335195ca7792fe3995f53d84d5e/compiler/src/AST/Canonical.hs), [optimized syntax](https://github.com/elm/compiler/blob/1bd5b36915a38335195ca7792fe3995f53d84d5e/compiler/src/AST/Optimized.hs), and [builder orchestration](https://github.com/elm/compiler/blob/1bd5b36915a38335195ca7792fe3995f53d84d5e/builder/src/Build.hs) support the narrower boundary comparison.

Elm itself publishes related artifacts and uses a separate annotation map. Thus the comparison cannot support a general prohibition on parallel products or side tables. It supports making their ownership and consumers explicit.

## Verification and limits

Validation combined source tracing, caller searches, comparator source inspection/counting, and existing executable contract tests. It did not benchmark an alternative architecture, prove historical causation, or discover a new reproducible compiler bug for every architectural smell.

The baseline checks and final documentation checks are recorded in the remediation plan's validation record. Existing source-level checks are the initial semantic floor; they do not prove a future refactor equivalent. The implementation must rerun the relevant suites and add narrowly targeted cross-boundary cases only where coverage is missing.

The two supplied Luna audits used `../src/...` links that resolved under `docs/src`, rather than the repository's source directory. Their link prefixes were repaired to `../../src/...`; their findings and estimates are preserved. Claims in the original files are not silently rewritten by this validation.
